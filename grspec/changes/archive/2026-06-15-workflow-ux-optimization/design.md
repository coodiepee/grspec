## Context

grspec currently uses a binary profile system (`core` vs `custom/expanded`) that gates command access. The `profile-tiers` spec already defines a four-tier system (`minimal`, `standard`, `full`, `custom`) but still treats profiles as access control rather than recommendation layers. Users who choose `minimal` lose access to `verify` even when they occasionally need it.

The archive flow currently outputs a minimal success message. There's no lifecycle feedback, no quality signal, and no awareness of remaining work. The explore skill has an implicit "offer to propose" behavior but no structured criteria for when to trigger it.

## Goals / Non-Goals

**Goals:**
- Make all CLI commands accessible regardless of profile (profiles control skill file generation, not CLI command availability)
- Add a non-blocking verify summary to archive output
- Add lifecycle feedback (stats, next steps) to archive completion
- Define structured crystallization criteria for explore-to-propose transitions
- Maintain backward compatibility with existing `core` profile users

**Non-Goals:**
- Removing the profile system entirely (profiles still control which skill files are generated)
- Making verify a hard gate on archive (it remains informational)
- Auto-creating proposals from exploration (user must explicitly opt in)
- Redesigning the verify skill's full report format
- Wiki integration changes (out of scope for this change)

## Decisions

### 1. Profiles control skill generation, not CLI dispatch

**Choice**: Profile determines which `.cursor/skills/` (or equivalent) files are generated by `grspec update`. The CLI itself SHALL execute any valid command regardless of profile.

**Alternatives considered**:
- Remove profiles entirely → Rejected because skill-file count affects AI context window; users with constrained context budgets benefit from minimal installs.
- Keep profiles as hard gates → Rejected because it creates artificial friction when users occasionally need a command outside their tier.

**Rationale**: The real cost of an unused workflow is context pollution in AI prompts, not CLI availability. A user running `grspec archive` manually doesn't need the archive skill file — they're already invoking it directly.

### 2. Lightweight verify as a pure-read pass

**Choice**: Archive's verify step SHALL only read existing artifacts (plan.md checkbox count, delta spec requirement headers) and compare against file system existence. It SHALL NOT do deep semantic analysis (that's `/grsx:verify`'s job).

**Alternatives considered**:
- Full verify on archive → Rejected because it adds significant latency and duplicates `/grsx:verify` without user opt-in.
- No verify at all → Current state; rejected because users frequently archive without knowing they missed requirements.

**Rationale**: The goal is a <500ms informational pass that catches obvious gaps. Task completion is a simple regex count; requirement coverage checks file existence patterns from spec requirement names.

### 3. Crystallization as skill-level guidance, not CLI enforcement

**Choice**: Crystallization detection lives in the explore skill template (`.cursor/skills/grspec-explore/SKILL.md`), not in CLI code. The agent evaluates criteria conversationally.

**Alternatives considered**:
- CLI command (`grspec explore --check-crystallization`) → Rejected because crystallization is a judgment call during conversation, not a verifiable state.
- Automatic proposal creation → Rejected because it removes user agency.

**Rationale**: Crystallization is inherently subjective. The skill template can define criteria (goal clarity, approach direction, scope bounds) that the AI evaluates during conversation. This keeps it adaptive to context.

### 4. Archive feedback uses existing data sources

**Choice**: Lifecycle stats SHALL be derived from:
- Task count: parse plan.md checkboxes (already done by archive's task-completion gate)
- Spec impact: count requirements in delta spec files (already parsed for merge)
- Change age: proposal frontmatter `created` date vs current date
- Active changes: `fs.readdir` on `grspec/changes/` excluding `archive/`

**Alternatives considered**:
- Maintain a metadata file tracking change events → Rejected because it adds state management for minimal benefit.
- Query git log for change activity → Rejected because it couples to git presence and adds latency.

**Rationale**: All required data is already available in the archive flow. No new I/O or state management needed.

## Implementation Strategy

| Component | Strategy | Notes |
|-----------|----------|-------|
| Profile resolution change | Manual refactor | Modify `resolveProfile()` to only gate skill generation |
| CLI command dispatch | Verify no-op | Confirm CLI already dispatches without profile check |
| Archive verify summary | TDD | New function: `compactVerifySummary(changeDir)` |
| Archive lifecycle feedback | TDD | New function: `archiveCompletionFeedback(changeDir, mergeResult)` |
| Explore skill template update | Manual edit | Add crystallization criteria to SKILL.md |
| Documentation updates | Manual edit | Update workflows.md, cheatsheet.md |

## Risks / Trade-offs

**[Risk: Profile semantic change confuses existing users]** → Mitigation: The `core` alias already maps to `standard` (per existing spec). The change is that CLI commands no longer refuse to run — existing users gain access without losing anything. The one-time hint about adding workflows to profile provides discoverability without blocking.

**[Risk: Lightweight verify gives false confidence]** → Mitigation: The compact summary explicitly states what it checks (task count, file existence) and recommends full `/grsx:verify` for deeper analysis. It never says "all good" without qualifying the check depth.

**[Risk: Crystallization criteria too rigid/too loose]** → Mitigation: Criteria are defined in a skill template (editable by users), not hardcoded. The initial criteria (goal + approach + scope) are intentionally broad. Users can tighten/loosen by editing the skill.

**[Risk: Archive output becomes too verbose]** → Mitigation: Lifecycle feedback and verify summary together add ~8 lines. The `--quiet` flag (if it exists) or `--skip-verify` can suppress them.
